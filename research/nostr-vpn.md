## 1. Control plane design: signed rosters, enrollment, roster sync

**What is a network / device.**
- The device identity is the Nostr identity key: "The Nostr identity key authenticates the device, signed rosters, admin actions, FIPS identity, and paid-exit offers/control." `nsec`/`npub` are normalized to hex internally. [source: docs/protocol.md, "Identity And Network IDs"]
- A **network** is identified by a `network_id` that "scopes the roster, LAN discovery, and deterministic tunnel addresses." Only **one configured network is active** in the live runtime. [source: docs/protocol.md "Scope" and "Identity And Network IDs"]
- Each member device gets a **deterministic derived IPv4** `10.44.x.y/32` = `SHA256(normalized_network_id + "\n" + device_pubkey_hex)` bytes mod 254. The doc stresses: "The address is deterministic, not an identity credential. Packet admission is still tied to the authenticated FIPS source and current route map." [source: docs/protocol.md, address formula]

**Who signs what.**
- A **version-1 signed roster event** contains: network ID and name, device and admin public keys, per-member aliases, signing time and signer identity. It is signed by an **admin** device key. "For an existing network, a newer roster is accepted only from a configured admin." Removing your own device from a roster removes the network locally. Stale, duplicate, invalid, or far-future rosters are rejected. [source: docs/protocol.md "Signed Rosters And Capabilities"]
- Routes and transport addresses are deliberately **not** roster fields: "Connected members exchange authenticated capability frames containing advertised routes, endpoint hints, and a timestamp. Capabilities expire from runtime use and never grant membership." [source: docs/protocol.md, same section]

**Enrollment / approval.**
- An unapproved device creates a short-lived `nvpn://join-request/…` bootstrap containing: stable device AppKey, a **separate ephemeral request identity and secret**, timestamps, optional device label. It deliberately contains no network ID, no membership, no admin list, no relay config. [source: docs/protocol.md "Join Approval"; docs/agents.md "Request access from the agent host"]
- The admin imports the request, adds the device to the network, and "creates a fresh Nostr-signed roster **bound to that request secret**." Delivery is "a stateful FIPS-TCP control exchange," not a public relay event. The joiner accepts only if: request matches, signature valid, signer is an admin, joiner is in the roster, freshness checks pass; the joiner **persists the roster before acknowledging**, and the admin keeps a durable delivery outbox until that exact receipt arrives. [source: docs/protocol.md "Join Approval"]
- Approval is explicitly **manual**: "Approval is not automatic. The admin app signs and distributes the updated roster." Headless/agent CLI flow: `nvpn join-request --json` produces the link; `nvpn join-requests inspect` and `join-requests approve` sign the updated roster and queue it over FIPS delivery; `"delivery": "queued"` ≠ received. [source: README.md "CLI Quick Start"; docs/agents.md "Review and approve on the admin host" — note headless approval commands are source-only, not yet in a release]
- The admin's roster signature remains the authority even for receipt-backed out-of-band manual joins (network/admin/device tuple). [source: docs/protocol.md "Join Approval"]

**Roster sync over Nostr — which events, encrypted or not?**
- Roster updates are **Nostr-signed events**, but primary delivery is the authenticated FIPS-TCP control channel, not a relay broadcast; relays "carry signed discovery/pubsub events, not private IP datagrams." [source: docs/protocol.md "FIPS Connectivity And Control"]
- The protocol doc does **not** specify a NIP event kind number or payload encryption for roster events — nvpn uses a custom event/`nvpn://` URI scheme envelope, not a registered NIP. `FipsControlFrame` is "a versioned nvpn application envelope carried as opaque FIPS payload … not a FIPS protocol message or wire-format extension." [source: docs/protocol.md "Canonical Source", "FIPS Connectivity And Control"]
- Paid-exit offers are separate expiring Nostr events signed by the seller (discovered via Nostr pubsub: `nostr-pubsub`, `nostr-pubsub-fips`, `nostr-pubsub-relay` crates). Release notes also mention signed update/hashtree roots fetched from relays and Negentropy reconciliation of discovery events. [source: docs/protocol.md "Paid Exits"; CHANGELOG 4.1.18/4.1.2; Cargo.toml deps]

**Routing admission.**
- Before an IP packet reaches the TUN, `FipsMeshRuntime` maps "the authenticated FIPS identity to a roster or paid-route admission and validates the packet source and destination." Outbound selection is longest-prefix over fresh capability frames; equal-specificity routes from different peers are ambiguous and dropped; leak protection withholds default routing until the protected path is ready. [source: docs/protocol.md "FIPS Connectivity And Control", "Routing And Exits"]
- Canonical implementations: `crates/nostr-vpn-core/src/{join_requests,signed_rosters,fips_control,fips_mesh,paid_routes}.rs`. [source: docs/protocol.md "Canonical Source"]

## 2. How it uses the FIPS data plane, and what the fork changed

**Features used (per nostr-vpn docs).**
- "FIPS is the only private-mesh dataplane. Depending on configuration it can use UDP, LAN discovery, static endpoints, authenticated bootstrap/transit peers, **Nostr-assisted endpoint discovery**, WebSocket, and optional **WebRTC** transport." nvpn passes endpoint hints, STUN servers, discovery policy and listen port into FIPS; FIPS observes/advertises overlay endpoints and does NAT traversal and path recovery. PCP/NAT-PMP/UPnP mapping remains an nvpn runtime aid. Publishing the operator-supplied exact UDP endpoint publicly is opt-in and **off by default**. [source: docs/protocol.md "FIPS Connectivity And Control", "Discovery And NAT"]
- Nostr relays carry signed discovery/pubsub events only; public bootstrap/discovered peers may relay FIPS traffic "without joining the private network." [source: docs/protocol.md]
- TUN-based private IP routing, authenticated at packet-admission time (see §1). [source: docs/protocol.md]

**FIPS itself (fork vs upstream jmcorgan/fips).**
- The fork's README: "This fork preserves the FIPS protocol surface while substantially redesigning the data plane for high packet rates. In comparable direct-path benchmarks it delivers roughly **three times** the original implementation's throughput. Most of the gain comes from an owner-affine, end-to-end batched pipeline that keeps packet buffers and session state resident, batches I/O and cryptography, reuses packet storage, and avoids packet-by-packet queue hops, allocations, copies, and repeated lookups." Libraries are published under the `nvpn-fips-*` crate namespace, with pinned release-input verification (`docs/library-releases.md`). [source: https://raw.githubusercontent.com/mmalmi/fips/master/README.md, intro + "License"]
- Fork-specific additions vs upstream visible in README/commits: optional **paid forwarding** policy (prepaid transit / bounded peer credit, `fips-credit`, Cashu `fips-relay`, "bounded replies" for one-way paid traffic), **WebRTC** transport (nostr-vpn enables `nvpn-fips-core` feature `webrtc-transport`), LAN-traversal candidates, dual-stack carrier connections, wallet-backed relay; commit subjects Nov 2026 show continuous session-recovery/rekey work ("Renew idle link keys when authenticated neighbor traffic resumes", "Harden FSP ingress", "Verify service traffic and rekey through upstream transit"). Many commits are co-authored with `claude` (AI-assisted development). [source: fips README "Optional paid forwarding"; fips commits page Nov 2026; nostr-vpn Cargo.toml]
- Upstream jmcorgan/fips (v0.6.0-dev, release v0.5.2) is broader in transports (UDP, TCP, Ethernet, Tor, **Nym**, BLE), has a native datagram API, LAN gateway, peer ACL, and packages for Debian/Arch/NixOS/macOS/OpenWrt/FreeBSD/pfSense/Windows — but no WebRTC, no paid forwarding, no published crates ("Published crate" is longer-term). Both are MIT. [source: https://raw.githubusercontent.com/jmcorgan/fips/master/README.md "Features", "Status & roadmap"]
- Fork versioning is very fast: nvpn-fips core/endpoint went 0.4.34 (nostr-vpn 4.1.0, 2026-07-21) → 0.4.123/0.4.124 (Nov 2026) while "preserv[ing] wire formats." [source: CHANGELOG 4.1.0/4.1.12; fips commits]

## 3. Feature set at protocol level

- **MagicDNS**: "MagicDNS names are always answered locally." With an active exit, policies are `automatic` (DNS IPs from a ready WireGuard profile, else built-in Cloudflare DoH), `encrypted` (Cloudflare/Quad9/custom DoH with literal bootstrap IPs), or `through_exit` (raw DNS wire messages to explicit IP resolvers over the exit). "Resolver or path failure is fail-closed; secure DNS does not fall back to system or plaintext DNS." Honest limits documented: DoH hides queries from the exit but the exit still sees destination IPs, timing, volume, and sometimes TLS SNI. [source: docs/protocol.md "Exit DNS And Inbound Safety"]
- **Subnet routes**: advertised in authenticated, expiring capability frames between connected members (not the roster); longest-prefix match; ambiguous equal-specificity routes dropped. [source: docs/protocol.md "Signed Rosters And Capabilities", "Routing And Exits"]
- **Exit nodes**: a selected private exit is usable only while the advertising peer is connected; "Selected FIPS exits are treated as hostile inbound networks" — reply-only admission for locally originated flows, valid ICMP errors quoting tracked flows; unsolicited/malformed/fragmented/private/spoofed mesh-source traffic dropped before the TUN, IPv4 and IPv6. [source: docs/protocol.md "Routing And Exits", "Exit DNS And Inbound Safety"]
- **WireGuard upstream egress**: an exit provider forwards admitted member traffic "through its selected local internet source: the host's direct path, a local WireGuard upstream, or another private FIPS exit"; WireGuard "is never a private-mesh transport." Implementation uses `boringtun` (userspace). Changelog shows per-platform WireGuard-exit release gates (provider-side forwarding, profile DNS, DNS/route restoration). [source: docs/protocol.md "Routing And Exits"; Cargo.toml `boringtun = "0.7"`; CHANGELOG 4.1.3/4.1.5]
- **Paid exits (Cashu)**: sellers sign expiring, parameterized **Nostr offer events** (price, Cashu mint/channel terms, IP support, coarse location, endpoint hints) that "grant no roster membership." Buyer establishes a **Cashu Spilman payment channel** and sends a paid-route session-open frame over authenticated FIPS-TCP; seller validates buyer+terms before granting admission scoped to the paid session (with hard exclusions of private/loopback/link-local/multicast/seller-mesh destinations). Byte-metering at the FIPS/nvpn boundary: buyer→exit packets billable immediately; exit→buyer billable only for recent buyer-originated UDP flows; TCP downloads billable on buyer acknowledgment, retransmissions not double-billed. Signed payment updates/acks ride FIPS control; expired seller channels with pending signed credit are auto-collected into the wallet with backoff and resume-after-restart; buyers can reclaim uncollected funds after 24h. Offers v2 are byte-only, normalized per-GB; automatic renewal authorized via `nvpn paid-exit buy <offer> --auto-renew`. Sellers can resell (Direct, WireGuard, or another private FIPS exit). Provider selection can be automatic using connection quality, price, and **signed ratings from trusted authors** distributed over Nostr. [source: docs/protocol.md "Paid Exits"; README.md "Paid Exits"; CHANGELOG 4.1.0 (v2 byte-only offers), 4.1.14 (ratings)]
- **File transfer** between peers also exists (`nvpn-fips-file-transfer` dependency; iOS file-offer notifications in 4.1.23). [source: Cargo.toml; CHANGELOG 4.1.23]

## 4. Maturity and quality signals

- **Release cadence**: crates.io shows **61 published versions of `nostr-vpn-core` between 2026-05-13 and 2026-11-19** (~6 months), roughly weekly-to-biweekly tagged releases (4.1.23 Nov 18, 4.1.22 Nov 14, 4.1.21 Nov 4, 4.1.20 Nov 3, 4.1.19 Oct 26, 4.1.18 Oct 19 …). The project passed 4.0.99 → 4.1.0 within July 2026. [source: https://crates.io/api/v1/crates/nostr-vpn-core `created_at`/`num_versions`; CHANGELOG.md dates]
- **Changelog tone**: exceptionally detailed and candid. Each release names concrete bugs (route ownership, DNS takeover, Cashu channel recovery, Windows service paths), **security fixes** (rustls 0.23.45 for RUSTSEC-2026-0285; "Fix cryptographic timing vulnerabilities in WebRTC connections"; NIP-04 IV rejection; QUIC peer-triggered crash fix; "Redact network join secrets from diagnostic bundles"; filesystem link/permission hardening on macOS/Linux), **measured performance results** (iPhone idle CPU 5.4% in 4.1.19 → 2.47% in 4.1.20 against a 2% target — reported as a **known issue** when missed), and even "Release process" lessons learned. [source: CHANGELOG.md 4.1.23–4.1.18, 4.1.12]
- **Platform app status**: native apps for macOS (App Store + TestFlight), Windows (x64), Linux (x64, deb/archives), Android (APK/Zapstore), iOS, web (WebVM), signed StartOS (Start9) `.s9pk` packages, multi-arch Umbrel image, `cargo install nvpn`. Desktop targets Apple-Silicon macOS + x64 Linux/Windows; mobile arm64; Intel macOS source-only. **iOS does not support paid exits.** A documented native-UI parity matrix tracks platform gaps. [source: README.md "Install", "Paid Exits"; docs/native-ui-parity-matrix.md referenced from README]
- **Test/verification tiers** (docs/verification-tiers.md): a 3-tier model — (1) `just verify-fast` per change (contracts, formatting, strict Clippy, dataplane/app-state safety, mobile shared behavior); (2) CI with parallel workspace tests, dataplane tooling, release-tooling contracts, web checks, platform compatibility; (3) `just verify-full` reserved native matrix locking a Mac, Windows SSH host, iOS simulator/device and Android device, running physical mobile VPN/TUN suites and a release gate with GUI lanes and a mandatory Windows WireGuard-exit lane; distinct exit codes for `infrastructure_unavailable` vs `product_failure`; opt-in destructive lab reset; plus a separate FIPS "dataplane safety net" (Docker/soak/roaming/host-pair/native runners) required for packet-path changes. Changelogs reference **physical-device release gates** (QR joins in both directions, Wi-Fi OFF→ON recovery, idle-CPU budgets). [source: docs/verification-tiers.md; CHANGELOG 4.1.5 "Added"]
- **Known issues**: 35 open issues, 57 PRs at time of research. **#79** (open, bug): regression in 4.1.18 — new `linux_host_network` DNS listener binds `:53` and collides with existing resolvers on Umbrel host-networking (Pi-hole); owner confirmed, prepared fix (separate stub address `127.0.0.55`, accept genuine native localhost resolvers, continue-without-DNS-takeover only when protected DNS is optional) verified against 47 Linux tests but **not yet in a release** as of 2026-11-19. Other recurring themes in "Known issues": iPhone idle CPU above target, a mesh timeout under a heavily loaded relay "still under investigation." [source: https://github.com/mmalmi/nostr-vpn/issues/79; CHANGELOG 4.1.20 "Known issues"; GitHub issues count]
- **Provenance caveat**: release verification relies on the author's own signing and a Hashtree-based signed-release updater reading from `git.iris.to`/Nostr blossom; GitHub is a mirror only. FIPS upstream says plainly: "The protocol and APIs are not yet stable," and nostr-vpn's protocol doc says "If this document and code differ, code wins." [source: README.md "Build and Verify"/canonical repo note; fips README "Status & Roadmap"; docs/protocol.md "Canonical Source"]

## 6. Reuse / fork viability for a third party

- **Legally trivial**: MIT everywhere (repo, core crate, FIPS fork, FIPS upstream); vendored payment crates are also published as normal crates.io packages (`nvpn-cashu-service`, `nvpn-cdk-spilman`) after a 4.1.13 "Cargo distribution repair" that pinned workspace deps so `cargo install nvpn` gets the real payment implementation. [source: LICENSE; crates.io features; CHANGELOG 4.1.13]
- **But architecturally coupled to its own app ecosystem**: the "core" crate carries config, diagnostics, MagicDNS, NAT, and WireGuard runtime **plus** the mobile-tunnel-facing app state (a separate `nostr-vpn-app-core` with UniFFI bindings feeds iOS/Android), the paid-exit wallet, social-graph trust/ratings, hashtree signed-updater, and the file-transfer crate. The CLI crate contains the actual Linux/macOS/Windows host-network plumbing (`linux_host_network`, `secure_dns_runtime`, `session_runtime`). A third party wanting "just the control plane" would import the roster/join/capability modules but drag along FIPS endpoint, nostr-sdk, and platform keyring deps. [source: docs/protocol.md "Canonical Source"; Cargo.toml members; crates/nostr-vpn-core/Cargo.toml]
- **Velocity and bus factor**: essentially one author (with AI pair authors "Dev"/"claude") shipping weekly releases across 7 platforms, with the canonical repo on `git.iris.to` and GitHub as a mirror; FIPS fork churns 0.4.x releases continuously. A fork would be chasing a fast-moving target; a *dependency* on `nvpn-fips-*` crates means trusting the same single publisher for the data plane. [source: crates.io publish history; fips commits page; README "canonical repository"]
- **Pragmatic read**: (a) the **most reusable layer** is the FIPS fork's `nvpn-fips-core/endpoint/tcp` crates (stable-ish wire formats, MIT, benchmarked 3× throughput) — usable directly as a mesh dataplane without any nostr-vpn control plane; (b) the **control-plane concepts** (signed rosters + capability frames + receipt-backed join protocol) are cleanly documented in docs/protocol.md and could be re-implemented against any transport in a few weeks; (c) forking the whole product makes sense only if you want the Cashu paid-exit marketplace or the 7-platform app stack as-is.

## 7. Gap analysis vs a "Tailscale but self-sovereign" spec

What it already covers (beyond a naive reading):

- Self-generated Nostr-key device identities, admin-signed rosters, manual join approval bound to a request secret with receipt confirmation, deterministic addressing, roster-gated packet admission, capability-frame route advertisement, encrypted-by-default DNS, leak protection / fail-closed behavior, key separation (device AppKey vs ephemeral request identity). [source: docs/protocol.md throughout]

What is **missing or weaker** than such a spec would need:

- **No ACL / policy layer**: rosters are flat member lists with aliases. There is no per-pair or per-subnet access policy, no tags/roles, no device posture — any member can reach any member's advertised routes. Tailscale's ACL model (and even FIPS-upstream's per-npub allow/deny link ACL, which the fork's README does not list) has no nostr-vpn equivalent. [source: docs/protocol.md "Signed Rosters And Capabilities" — roster fields are exhaustive; contrast jmcorgan/fips README "Peer ACL"]
- **No MLS-style group key agreement / control-plane forward secrecy**: roster events are signed but the doc nowhere describes encrypting the roster to members or ratcheting membership secrets; confidentiality of packet traffic comes from FIPS's Noise IK/XK with periodic rekey (the fork actively renews idle link keys), not from the control plane. A spec-grade design would want encrypted, forward-secret roster distribution. [source: docs/protocol.md; fips README "Two-layer encryption"; fips commit "Renew idle link keys…"]
- **No delegation or admin rotation story**: one active network, admin authority = "a configured admin" key; no documented multi-admin quorum, key rotation for a compromised admin, or sub-admin delegation. [source: docs/protocol.md "Join Approval", "Signed Rosters"; "Scope" (one active network)]
- **Non-standard Nostr usage**: custom event envelope, custom `nvpn://` URIs, no NIP event kinds — interoperable "self-sovereign" control plane (other clients parsing the same events) is not possible yet; relay-visible roster/offer metadata (network IDs, seller offers, ratings) is public-by-design. [source: docs/protocol.md; CHANGELOG]
- **No device revocation granularity beyond roster removal** (no key expiry, no session invalidation timestamp semantics documented beyond roster freshness checks), and no documented escape from a malicious admin other than self-removal. [source: docs/protocol.md]
- **Central-ish operational crutches**: operator-run public bootstrap pair, `git.iris.to` canonical repo + signed Hashtree release roots — fine for supply chain, but the "self-sovereign" story for *software updates* depends on the author's infrastructure. [source: README.md; CHANGELOG 4.1.21]
- Conversely, things it has that many self-sovereign specs lack: **paid exits with metered Cashu channels**, agent/headless enrollment design, deterministic addressing, receipt-based join confirmation. [source: docs/protocol.md; docs/agents.md]

## Verdict for noscat

**Fork vs reuse vs avoid — graded assessment:**

1. **Do not fork the whole product.** It is a 7-platform app + daemon + wallet + updater stack moving at weekly cadence under a single author, with canonical hosting on the author's own Nostr git server. Forking buys you a maintenance treadmill, not leverage.
2. **Selective dependency reuse is attractive and MIT-clean**: the `nvpn-fips-core`/`nvpn-fips-endpoint`/`nvpn-fips-tcp(-endpoint)` crates are the best-artifact here — a benchmarked (~3× upstream), actively hardened mesh dataplane with Nostr-native identities, Wire-format-preserving fast releases, MIT, published on crates.io. If noscat needs a mesh data plane, depending on these crates directly (or on upstream jmcorgan/fips if you prefer Tor/Nym/BLE transports and a more multi-platform maintainer) is the highest-value move.
3. **Treat the control plane as a reference design, not a dependency.** The signed-roster + receipt-backed join + capability-frame pattern in docs/protocol.md is exactly the right skeleton for a self-sovereign Tailscale-like control plane, and it is short enough to re-implement cleanly — which is also where noscat should differentiate: add ACLs/policy beyond flat rosters, MLS-style forward-secret roster distribution, admin delegation/rotation, and standard NIP-based event kinds that nostr-vpn currently lacks.
4. **`nostr-vpn-core` as a library: avoid.** Published but effectively private (1.9k downloads, no docs, exact-pinned versions, default features drag in Cashu/social-graph/vendored payment crates). Reuse its *ideas* and its FIPS crates, not the crate.
5. **Maturity signal is genuinely good** for the project itself (honest changelogs, physical-device release gates, security fixes, measured performance budgets) — a good upstream to *watch and borrow from*, while noting known rough edges (DNS takeover regressions like #79, iOS idle CPU, FIPS API instability).

**One-line verdict: borrow the dataplane (nvpn-fips-* crates), reimplement the control plane from its protocol doc with the missing MLS/ACL/delegation pieces, and don't fork the app.**
